# Credit Pilot

Минимальный каркас веб-приложения для кредитных заявок малого бизнеса.

## Структура

- `backend/` — Python 3.12, FastAPI, psycopg, каталог продуктов, API заявок и health.
- `backend/migrations/` — миграции Alembic; `backend/tests/` — API-тесты с PostgreSQL.
- `frontend/` — React, TypeScript и Vite; в Docker собранную страницу раздаёт nginx.
- `compose.yaml` — frontend, backend и PostgreSQL 17 с именованным volume.

## Состояние и документация

T01 закрыта после предварительной приёмки внешним ревью: API заявок, владение
по owner_id, серверные сессии/CSRF и application_events работают. Frontend пока
только показывает health; формы входа и кабинетов не реализованы.
T05 реализована: версионированный каталог двух учебных продуктов, финансовые поля,
валидация отправки и история. [API-контракт T05](docs/t05-api-contract.md) описывает
форматы и намеренное ужесточение submit для прежних черновиков.
Frontend/вход T06 и клиентская форма T07 остаются отдельными задачами.
T02 (перенос psycopg на SQLAlchemy) отложена и не блокирует эти задачи.

## Запуск

Нужны Docker Engine / Docker Desktop и Docker Compose v2 или новее.
Из корня репозитория:

```bash
cp .env.example .env
docker compose up --build
```

Для API заявок отдельно создайте локальные демоаккаунты (после запуска backend):

```bash
docker compose exec backend python seed.py
```

Seed идемпотентен: не очищает БД, не меняет существующие пароли и не присваивает
старые заявки новым аккаунтам. Frontend пока показывает только health и входа
не требует.

В `.env` задаются имя БД, пользователь, пароль и внешние порты. Значения
из примера предназначены для локального запуска. Не добавляйте `.env` в Git.
Backend получает параметры подключения из `POSTGRES_HOST`, `POSTGRES_PORT`,
`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`; внутри Compose адрес БД
и её порт заданы как `postgres:5432`.

Адреса при стандартных портах:

- Frontend: http://localhost:5173
- Swagger: http://localhost:8000/docs
- Health: http://localhost:8000/api/health

Откройте frontend: статус backend и БД обновляется каждые 5 секунд.
Запрос `/api/health` идёт через nginx на backend. При локальном запуске
Vite (`cd frontend && npm ci && npm run dev`) `/api` проксируется на
`http://localhost:8000`.

## Проверка

```bash
curl -i http://localhost:5173/api/health
docker compose stop postgres
curl -i http://localhost:5173/api/health
docker compose start postgres
```

При доступной БД ответ — HTTP 200 и `{"status":"ok","database":"ok"}`.
При недоступной — HTTP 503 и `{"status":"error","database":"unavailable"}`.
Страница отображает соответствующий статус. После запуска БД дождитесь
её готовности и следующего обновления страницы.

## Остановка

```bash
docker compose down
```

Данные остаются в именованном volume. `docker compose down -v` также удаляет
volume и все данные БД. Переменные `POSTGRES_*` инициализируют БД при первом
запуске с пустым volume; изменение `.env` не меняет существующих пользователей.

## Миграции backend

При обычном запуске контейнер backend выполняет `alembic upgrade head` перед
запуском API. Существующий volume сохраняется; миграция создаёт таблицу заявок.
Миграция 0004 добавляет каталог и nullable-поля продукта/финансов; старые заявки
сохраняются без выдуманных значений. Два продукта создаются самой миграцией.
Применить миграции отдельно, без запуска API:

```bash
docker compose up -d postgres
docker compose run --rm --build backend alembic upgrade head
```

## API заявок

API заявок требует локальную серверную сессию. CLIENT может создавать заявки
и читать/изменять/отправлять только собственные заявки (`owner_id`); BANK_EMPLOYEE — только читать заявку
и её историю. Без сессии — 401, чужая клиентская заявка — 404, неподходящая
роль — 403. Совпадение компании не даёт доступа к заявке другого пользователя.
Это минимальная основа доступа для T01, не законченный кабинет.
Используйте только синтетические данные.

Seed создаёт `client-a`, `client-b` и `bank`; пароли из `.env.example` предназначены
только для локального демо. Их можно задать через `DEMO_CLIENT_PASSWORD`,
`DEMO_CLIENT_B_PASSWORD`, `DEMO_BANK_PASSWORD` **до первого seed**.
Роли клиентов — `CLIENT`, роль аккаунта `bank` — `BANK_EMPLOYEE`. Роль,
идентификатор пользователя и владелец заявки определяются сервером по сессии;
заголовки или поля frontend для назначения этих значений не принимаются.
Пароли хешируются PBKDF2-SHA256; токены сессии и CSRF в БД хранятся только хешами.
Cookie HttpOnly/SameSite=Lax, срок 8 часов; `/api/auth/logout` отзывает сессию.
Защита от перебора, UI входа и управление аккаунтами ещё не реализованы.

Сейчас CSRF-токен возвращает только login, `/api/me` его не выдаёт. Восстановить
токен из csrf_hash нельзя. Предложение для T06 — sessionStorage для reload той же
вкладки; при пустом storage нужна явная повторная аутентификация. Это ещё не
реализовано во frontend; подробности и ограничения — в [архитектуре](docs/architecture.md).

Войти и сохранить cookie и CSRF-токен в текущей shell-сессии (нужен Python 3):

```bash
CREDIT_COOKIE_JAR=$(mktemp)
CREDIT_CSRF=$(curl --fail --silent --show-error -c "$CREDIT_COOKIE_JAR" \
  -X POST http://localhost:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"client-a","password":"demo-client-a-local"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["csrf_token"])')
```

Для любого изменения нужны cookie и `X-CSRF-Token`. Если браузер прислал Origin,
он должен входить в `ALLOWED_ORIGINS` (адреса без завершающего `/`). При изменении
портов добавьте соответствующие адреса. Для HTTPS включите `COOKIE_SECURE=true`;
публичное развёртывание требует отдельной проверки безопасности.

Получить каталог после входа:

```bash
curl -b "$CREDIT_COOKIE_JAR" http://localhost:8000/api/products
```

Каталог содержит действующие версии WORKING_CAPITAL (50 000–3 000 000 ₽,
3–24 мес., учебные 20% годовых) и EQUIPMENT (100 000–5 000 000 ₽,
6–36 мес., учебные 18%). Границы включительные, `annual_rate` — десятичная
доля строкой (`"0.20"` / `"0.18"`). Это **Предложение команды**, не условия банка.

Редактируемые поля: `company_name` (до 255 символов), `inn`, `credit_purpose`
(до 1 000 символов), `amount` (рубли), `term` (целое число месяцев),
`product_code` (до 64 символов), `monthly_revenue`, `monthly_operating_expenses`,
`existing_monthly_debt_payments` (рубли за месяц).
В черновике поля можно пропускать или очищать через `null`; текст допускает
пустые строки. Пустые строки в деньгах, `term` и `product_code` превращаются в `null`.
При PATCH отсутствующие поля сохраняют прежние значения.

Все денежные поля хранятся в PostgreSQL как точный `NUMERIC`, без округления. Допустимы
конечные значения максимум с двумя знаками после запятой, в том числе в черновике.
Например, `1.001` и `1.230` отклоняются. JSON принимает сумму числом или строкой;
рекомендуется десятичная строка, чтобы клиент не терял точность. В ответе деньги
возвращаются строками. `term` передаётся JSON-целым числом в диапазоне PostgreSQL
`BIGINT` (от −2⁶³ до 2⁶³−1).

Сервер назначает `id` (номер из последовательности БД), `created_at`, `updated_at`
и статус `DRAFT`, а `owner_id` берёт из сессии. Передать эти поля при создании
или PATCH нельзя. Существующие `company_id` и `created_by` сохранены для
совместимости, но проверка владения использует только `owner_id`.
Номера могут иметь пропуски. Метки времени содержат часовой пояс.

Создать неполный черновик (HTTP 201):

```bash
curl -b "$CREDIT_COOKIE_JAR" -H "X-CSRF-Token: $CREDIT_CSRF" \
  -X POST http://localhost:8000/api/applications \
  -H 'Content-Type: application/json' \
  -d '{"company_name":"Тестовая компания"}'
```

Подставьте полученный `id` вместо `1`. Прочитать и дополнить заявку:

```bash
curl -b "$CREDIT_COOKIE_JAR" http://localhost:8000/api/applications/1

curl -b "$CREDIT_COOKIE_JAR" -H "X-CSRF-Token: $CREDIT_CSRF" \
  -X PATCH http://localhost:8000/api/applications/1 \
  -H 'Content-Type: application/json' \
  -d '{"inn":"1234567890","credit_purpose":"Закупка оборудования","amount":"125000.25","term":12,"product_code":"EQUIPMENT","monthly_revenue":"200000.00","monthly_operating_expenses":"100000.00","existing_monthly_debt_payments":"10000.00"}'
```

Отправить заявку:

```bash
curl -b "$CREDIT_COOKIE_JAR" -H "X-CSRF-Token: $CREDIT_CSRF" \
  -X POST http://localhost:8000/api/applications/1/submit
```

Отправка требует прежние пять полей, продукт и три финансовых значения.
Название и цель не должны состоять только
из пробелов, ИНН — ровно 10 или 12 ASCII-цифр (без проверки контрольной суммы),
сумма и срок — в границах действующей версии выбранного продукта.
Выручка >0, расходы и существующие выплаты ≥0; расходы могут превышать выручку.
`product_version` — серверное поле: в DRAFT оно `null`, submit фиксирует
действующую версию (`product_v1`) вместе со статусом и событием.
Успешная отправка возвращает HTTP 200 и статус
`SUBMITTED`. При ошибке валидации (HTTP 422) данные и метки времени не меняются.
Редактировать и повторно отправлять `SUBMITTED` нельзя (HTTP 409).
Несуществующий номер возвращает HTTP 404. Решения сотрудников пока отсутствуют.

Старые пяти-полевые черновики теперь намеренно получают 422 на submit до заполнения
продукта и финансов. Старые SUBMITTED читаются с `null` в новых полях, автоматически
не изменяются. Условия опубликованной версии продукта неизменны в БД; смена
действующей версии не переписывает отправленные заявки.

## История заявки (T01)

```bash
curl -b "$CREDIT_COOKIE_JAR" http://localhost:8000/api/applications/1/events
```

События `DRAFT_CREATED`, `DRAFT_UPDATED`, `SUBMITTED` сохраняются в PostgreSQL
в одной транзакции с изменением заявки. Каждое содержит номер заявки, время,
`actor_id` и роль из серверной сессии, предыдущий/новый статус, версию заявки
и изменения разрешённых бизнес-полей. Пароли, cookie, CSRF, заголовки и произвольное
тело запроса в журнал не копируются. Суммы в изменениях — десятичные строки.
Не вводите секреты в текстовые поля заявки.
Создание/PATCH включают продукт и финансовые поля, SUBMITTED фиксирует
`product_version` в changes как old=null/new=выбранная версия.

История доступна только владельцу заявки и BANK_EMPLOYEE. Чтение отсортировано по id
события; параметры `limit` (1–100, по умолчанию 100) и `after_id` позволяют читать
следующие страницы. API изменения/удаления событий нет. Это append-only журнал
на уровне приложения, не защита от администратора БД.

Пустой PATCH и повтор PATCH с уже сохранёнными значениями не меняют timestamps,
version и историю. Повтор submit возвращает 409 без второго события; параллельные
команды сериализуются блокировкой заявки. POST создания **не идемпотентен**:
каждый намеренный вызов создаёт новую заявку; автоматический retry после потери
ответа пока не поддерживается. Невалидная команда или ошибка записи события
откатывает всю бизнес-операцию.

Миграции `0002_application_events` и `0003_application_owner` применяются обычным
`alembic upgrade head` при старте backend. Применённая 0002 не изменялась.
0003 добавляет `owner_id`, переносит известного CLIENT-автора из `created_by`
и переименовывает роль `BANK` в `BANK_EMPLOYEE`, сохраняя события и сессии.
Заявки без известного автора сохраняются без владельца и без выдуманной истории:
CLIENT их не видит, BANK_EMPLOYEE может прочитать. Сопоставление
старых записей владельцам — отдельная будущая задача; seed этого не делает.
Перезапуск backend сохраняет события и действующие сессии.
Журнал входов/просмотров и полноценное управление доступом из архитектуры
остаются следующими задачами; T01 пишет бизнес-события создания/PATCH/submit.

Для ручной проверки выполните создание, PATCH и submit из примеров выше:
история должна содержать ровно `DRAFT_CREATED`, `DRAFT_UPDATED`, `SUBMITTED`.
Повтор PATCH с теми же значениями до отправки не добавляет событие; повтор submit
возвращает 409. Войдите как `client-b` с отдельной cookie: чтение, изменение,
отправка и история заявки `client-a` должны вернуть 404. Аккаунт `bank` может
прочитать заявку и события, но создание, PATCH и submit возвращают 403.
После `docker compose restart backend` прежние cookie и история сохраняются
(дождитесь готовности health). Автотесты дополнительно проверяют изоляцию двух
пользователей одной компании.

Выйти и удалить временную cookie:

```bash
curl -b "$CREDIT_COOKIE_JAR" -H "X-CSRF-Token: $CREDIT_CSRF" \
  -X POST http://localhost:8000/api/auth/logout
rm "$CREDIT_COOKIE_JAR"
unset CREDIT_CSRF CREDIT_COOKIE_JAR
```

## Тесты backend

```bash
docker compose up -d postgres
docker compose run --rm --build backend sh -c 'pip install -r requirements-dev.txt && pytest -q'
```

Нужен доступ к реальному PostgreSQL. Тесты создают отдельную временную БД,
применяют к ней миграцию и удаляют её после прогона; данные основной БД
не изменяются. Пользователю БД нужно право `CREATEDB` (стандартный пользователь
PostgreSQL из Compose его имеет). Установка тестовых зависимостей требует сети.
Проверяются неполные черновики, PATCH, точность сумм, ошибки и успех отправки,
защита серверных полей, HTTP 404/409 и health.
Тесты также проверяют права, CSRF, session expiry/revoke, откат при ошибке журнала,
параллельные повторы, точность истории и обновление существующей схемы 0001.
Дополнительно проверяются запрет доступа другому пользователю той же компании
и обновление уже применённой 0002 без потери событий или сессий.
Тесты T05 проверяют каталог, границы обоих продуктов, точность всех финансовых
полей, неизменность версий, запрет отправки неполных старых черновиков и переход
0003→0004 с сохранением DRAFT/SUBMITTED, истории и сессий.
