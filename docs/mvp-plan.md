# План реализации MVP Credit Pilot

Статус на 21 октября 2026 года: T01 закрыта после предварительной приёмки
внешним техническим ревью. Архитектура предварительно согласована. Следующий этап
по решению пользователя — **T05 и параллельно T06**. T02 отложена.

Команда — 2–3 человека, бюджет разработки — 7 дней по информации пользователя,
а не из PDF. Приоритет — работающий сквозной путь и комплект сдачи. Детальный
календарь и официальный дедлайн здесь не выдумываются. Конкретные способы
реализации ниже — **Предложение команды**, если не отмечено решение пользователя.

## Что уже есть и что закрыто

- Три Docker-сервиса, PostgreSQL volume, Alembic 0001–0003, health 200/503.
- API создания, чтения, PATCH и отправки; DRAFT/SUBMITTED и точные Decimal.
- application_events с инициатором, временем, переходом, версией и old/new.
  Запись атомарна с заявкой, повторы PATCH/submit не дублируют события.
- CLIENT / BANK_EMPLOYEE, серверные сессии, CSRF, права через owner_id.
  Другой клиент, в том числе той же компании, не получает доступа.
- Локальный seed двух клиентов и сотрудника. Неизвестные legacy-владельцы
  не назначаются автоматически; журнал задним числом не выдумывается.
- Frontend — только страница health. Нет UI входа, форм, кабинетов или таймлайна;
  Tailwind/shadcn пока не подключены. Продуктов, финансовых полей и банковских
  команд/скоринга пока нет. Списка заявок в API тоже нет.

Код T01 сохранён в рабочей копии, включая новые untracked-файлы. Отсутствие commit
не означает отсутствие реализации; полный состав — [T01_REVIEW.md](T01_REVIEW.md).
При закрытии повторно прошли 54 backend-теста (8 deprecation warnings)
и сборка frontend. Бизнес-код, схема и зависимости при синхронизации не менялись.
При синхронизации документации Git index пуст и не изменяется. Документы безопасно
перенесены отдельно из korobov/docs, без merge кода и переключения ветки.

## Следующий этап — T05 и T06 параллельно

При 2–3 участниках один развивает backend-контракт T05, второй — frontend T06.
Согласование API/типов и интеграция общие; это порядок командной разработки,
не поручение агенту автоматически запускать обе задачи или подагентов.

| Направление | Небольшие последовательные инкременты | Проверка готовности |
| --- | --- | --- |
| T05. Продукты и финансовые поля | Сначала схема/seed и чтение двух продуктов; затем nullable product_code/version и monthly_revenue/monthly_operating_expenses/existing_monthly_debt_payments; затем явное расширение submit-валидации и истории | Миграция со старой схемы, старые заявки доступны по прежним правам; Decimal и неполные DRAFT сохранены; новые данные попадают в application_events; ограничения продукта проверяет сервер |
| T06. Frontend и вход | Сначала небольшая Tailwind/shadcn-основа; затем login/logout и роль через /api/me; затем восстановление состояния после reload и общий fetch с cookie/CSRF | Сборка, вход обеими ролями, reload той же вкладки, выход и 401/403; frontend не назначает роль/owner_id и не подменяет серверные права |

T05 не требует ORM-рефакторинга. Сначала согласовать контракт каталога и новых
полей; UI может разрабатываться по нему, но результат проверить с реальным API.
Существующие пять полей и пути сохранить. Старые DRAFT заполняются постепенно;
старые SUBMITTED не переписывать и не заполнять фиктивными данными автоматически.
Неполные старые SUBMITTED не допускать к будущей банковской обработке без отдельной
контролируемой процедуры получения необходимых данных.

В T06 **ещё не реализованное предложение** для reload: csrf_token из login хранить
в sessionStorage, bootstrap делать через /api/me. Токен не восстанавливается из
csrf_hash, а /api/me его сейчас не возвращает. При пустом storage и действующей
cookie нужен явный повторный вход перед изменениями. Для новых независимых
вкладок это ограничение; альтернативное bootstrap-решение требует отдельного
согласования. Подробности и проверки — [architecture.md](architecture.md).

После двух направлений — короткая общая проверка login → reload → создание/PATCH
через API с CSRF → logout. Полный клиентский экран заявки остаётся T07. Новая
авторизация или реализация T05/T06 в задачу синхронизации документации не входят.

## Риски и проверки

- CSRF теряется при хранении только в памяти. Проверить reload и новую вкладку
  в T06; sessionStorage-предложение не считать уже работающим кодом.
- Работа новой формы может потребовать новых полей, которых нет в старых записях.
  T05 обязана явно определить nullable-переход и правила отправки.
- Row lock и version есть, но expected_version нет: разные обновления поля
  работают как last-write-wins. Для банковских решений предусмотреть конфликт.
- POST создания не идемпотентен; не добавлять автоматический retry после потери ответа.
- История append-only только на уровне API; нет аудита входов/просмотров,
  rate limiting и автоматической очистки старых сессий. Это ограничения демо.
- Ставки и скоринговые пороги — учебные предложения команды, не правила банка.
- Новостная лента в PDF неоднозначна; уточнение у организаторов остаётся открытым.
- Один PostgreSQL не даёт HA; показ восстановления не означает production readiness.

На каждом инкременте: релевантные unit/API/PostgreSQL-тесты и сохранение health;
для UI — сборка и затронутый браузерный сценарий; для миграций — новая/старая БД.
Время 7 дней направлять на сквозной путь, не на необязательный рефакторинг.
