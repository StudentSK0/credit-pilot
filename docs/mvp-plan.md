# План реализации MVP Credit Pilot

Статус: проект для согласования. **Предложение команды:** приоритеты, порядок,
размер задач и критерии готовности ниже. PDF не задаёт сроки, состав команды
или веса критериев. Даты дедлайна в прочитанном документе нет; её нужно получить
у организаторов перед фиксацией версии сдачи.

## Что уже есть

Работающий каркас из трёх Docker-сервисов, health, API создания/чтения/PATCH
черновика и отправки, миграция 0001, backend-тесты. В репозитории эти изменения
присутствуют, часть подготовлена в Git index. Это не полноценный MVP: отсутствуют
владельцы и доступ, каталог, банковские команды, скоринг, аудит и формы кабинетов.
Утверждать готовность новых функций можно только после их реализации и проверок.

## Правило работы небольшими шагами

Один рабочий заход — одна задача из таблицы, либо ещё меньшая часть по соглашению.
После неё: что изменилось, как проверено, какие ограничения остались. Не переходить
автоматически к следующему большому этапу. Не переписывать backend/frontend ради
соответствия всей архитектуре за один заход. Каждый инкремент сохраняет запуск
Compose и текущий health; существующие API-тесты остаются регрессией.

Сначала согласовать эту архитектуру и объём. В текущей задаче меняются только
пять документов в docs и AGENTS.md. Приложение, БД и зависимости не меняются.

## P0 — сохранить основу и сделать процесс безопасным

| Задача | Узкий результат | Критерий готовности и связь |
| --- | --- | --- |
| T01. Аудит существующих команд | Таблица событий, атомарная запись создания, PATCH и submit; API истории | Успех пишет событие, невалидный submit не меняет заявку, данные переживают рестарт; R05, U04 |
| T02. Доступ к данным через SQLAlchemy | Вынести текущие команды в сервис/репозиторий и перенести запросы с psycopg без изменения поведения | Все прежние тесты плюс аудит проходят на PostgreSQL; миграция 0001 не переписана; U05 |
| T03. Владельцы и демоданные | Company/User, company_id/created_by/version, явное сопоставление старых синтетических заявок, seed двух клиентов и сотрудника | Повтор seed не дублирует записи; старые данные не теряются и не назначаются случайно; R10 |
| T04. Локальная аутентификация и права | Серверные сессии, login/logout/me, CSRF, проверки компании и роли | S07 на каждом маршруте; чужие данные не выдаются; сессии отзываются; U01, R14 |

T01 не требует сразу полной банковской схемы. Пока нет аутентификации, событие
имеет честный технический actor LEGACY/ANONYMOUS, а не выдуманного клиента.
После T04 новые действия всегда связаны с реальным тестовым actor.
T03 и T04 при необходимости делятся на отдельные задачи для схемы, seed и API.

## P1 — клиент может выбрать продукт и подать заявку

| Задача | Узкий результат | Критерий готовности и связь |
| --- | --- | --- |
| T05. Каталог и данные для оценки | Две версии учебных продуктов, API каталога, финансовые поля; новые проверки submit | Границы продукта, Decimal, неполные черновики и совместимость старых записей проверены; R03, U03 |
| T06. Общий UI и вход | Небольшая Tailwind/shadcn-основа, локальный вход, навигация по роли | Чистая frontend-сборка, выход работает, роль не берётся из localStorage; U01/U05 |

## P2 — банковское рассмотрение и объяснение результата

| Задача | Узкий результат | Критерий готовности и связь |
| --- | --- | --- |
| T08. Банковская очередь и старт обработки | Список/досье BANK, расширение состояний, команда старта и таблица ProcessingRun | Клиент не вызывает команду; переход и события атомарны; R04/U02 |
| T09. Локальные проверки | REGISTRY/BKI fixtures, COMPLETE/INCOMPLETE/FAILED, повтор и stale-run | S05/S08, неизвестный ИНН не становится успешным результатом; R16 |
| T10. Объяснимый скоринг | Чистая функция score_v1, снимки и факторы; policy_v1 отдельно | Контрольный вектор и все границы из architecture.md; рекомендация не подменяет решение; U03 |
| T11. Цикл уточнений | InformationRequest, ограниченный ответ клиента, повтор обработки | S02; два набора входов и два результата сохранены; R04/R05 |
| T12. Решение сотрудника | OFFER/REJECT, причины, отдельные условия и повторная оценка меньшей суммы | S03/S04/S06; жёсткие ограничения нельзя обойти; R04 |
| T13. Банковский UI и клиентский результат | Очередь, факторы, запрос сведений, решение; клиентский экран запроса и предложения/отказа | S01 до OFFERED, S02/S03 через два браузерных сеанса; R03/R04 |

T08–T12 сначала проверяются API-тестами. T13 допустимо разделить на очередь,
уточнения и решение, чтобы не делать весь банковский кабинет одним изменением.
Сначала обеспечить обычное предложение и отказ, затем в отдельном заходе
добавить меньшую сумму; до неё S04 явно отмечается как ещё не реализованный.

| Задача | Узкий результат | Критерий готовности и связь |
| --- | --- | --- |
| T14. Симуляция оформления | Документ условий из шаблона, подтверждение подписи, одна запись выдачи | S01 до DISBURSED и S06, маркировка симуляции во всех экранах; R18 |
| T15. Минимальная лента | Локальные материалы с содержанием и условиями показа | S09; трактовка спорного пункта с. 7 отмечена в README |
| T16. Проверка сдаваемой версии | Seed сценариев, README, THIRD_PARTY_NOTICES, OpenAPI, коллекция запросов и сценарии проверок | S01–S10, чистый запуск, комплект R06–R13; после сборки нет внешней runtime-зависимости |

Документация и тесты обновляются на каждой задаче; T16 — сверка и упаковка,
а не первый момент написания README. Закрепление версий образов и полного
набора runtime-зависимостей выполняется до финальной чистой сборки.
Git commit/tag, доступ жюри и публикация согласуются отдельно: описание PDF
не является разрешением агенту выполнить commit, push или открыть доступ.

## Проверки по уровням

- Unit: формулы Decimal, границы факторов, политика, таблица переходов.
- Integration на PostgreSQL: миграции с нуля и со старой схемы, row locks,
  версии, атомарность события и команды, сохранение истории.
- API: валидация, 401/403/404/409/422, ownership, неизменность при ошибке,
  идемпотентность подписи/выдачи и стабильность health.
- Browser: обе роли, сохранение черновика, уточнения, результат и лента;
  клавиатурная навигация, ясные ошибки, отсутствие JavaScript-ошибок.
- Deployment: Compose на чистом окружении, seed, восстановление после рестарта,
  сценарий без исходящего интернета после загрузки образов.

Проверять только относящееся к очередному изменению, затем полный сквозной путь
на контрольных этапах P1/P2/P3. Не добавлять тесты, которые лишь копируют код
или требуют платной/корпоративной инфраструктуры.

## Риски и решения для согласования

| Риск | Последствие | Предложение команды |
| --- | --- | --- |
| Неясный пункт новостной ленты | Разная трактовка экспертами | Уточнить у организаторов; до ответа сохранить T15 в объёме |
| Нет сведений о дедлайне и ресурсах команды | Нельзя честно обещать календарные сроки | Планировать по готовым инкрементам; календарь после уточнения ресурсов |
| Слишком много функций до первого рабочего пути | Демонстрация распадается на экраны | P1, затем базовые OFFER/REJECT; альтернативные условия и симуляции — следующими шагами |
| Учебные пороги воспринимаются как банковские | Недостоверные заявления о риске | Явные labels, версии, fixtures и отсутствие PD; не заявлять точность без данных |
| Старые заявки без владельца и продукта | Утечка между демоклиентами или потеря данных | Явное сопоставление, staged migration, S07; не очищать volume |
| Два сотрудника/повтор запроса | Двойное решение, подпись или выдача | Row locks, version, UNIQUE, S06 |
| Сбой между стартом и завершением проверки | Зависшая заявка | Durable run, таймаут и безопасный повтор, S08 |
| Выбор авторизации откладывается | Кабинеты изолированы только визуально | T04 до полноценных интерфейсов; проверка каждого API |
| Стенд зависит от внешних данных/ключей | Жюри не может запустить | Симуляторы и fixtures в образе, S10 |
| Один сервер и одна БД | Нет промышленной отказоустойчивости | Честно показать восстановление, не обещать HA и production readiness |

## Что согласовать перед кодом

Предлагается утвердить два учебных продукта, девять состояний, одну банковскую
роль, локальные аккаунты, score_v1/policy_v1 и положительную ветку с симуляциями.
Ближайший рабочий инкремент после согласования — **только T01: история текущих
команд черновика/отправки**. Остальные задачи остаются планом, не разрешением
реализовать всё за один заход.
