# T05 — API каталога и финансовых данных заявки

Контракт для интеграции frontend T07. Основа: [архитектура](architecture.md),
[модель данных](domain-model.md). Условия продуктов и правила финансовых полей —
**Предложение команды**, учебные синтетические данные, не предложения Альфа-Банка.
Скоринг, решения и новые статусы в T05 не входят.

## Каталог

`GET /api/products` возвращает HTTP 200 и JSON-массив действующих версий,
отсортированный по `code`. Нужна действующая серверная сессия CLIENT или
BANK_EMPLOYEE; CSRF для GET не нужен. Пустой каталог — `[]`.

```json
[
  {
    "code": "EQUIPMENT",
    "version": "product_v1",
    "name": "Приобретение оборудования",
    "currency": "RUB",
    "min_amount": "100000",
    "max_amount": "5000000",
    "min_term": 6,
    "max_term": 36,
    "annual_rate": "0.18"
  },
  {
    "code": "WORKING_CAPITAL",
    "version": "product_v1",
    "name": "Пополнение оборотных средств",
    "currency": "RUB",
    "min_amount": "50000",
    "max_amount": "3000000",
    "min_term": 3,
    "max_term": 24,
    "annual_rate": "0.20"
  }
]
```

| Поле карточки | Тип и смысл |
| --- | --- |
| code | Строка, стабильный код продукта |
| version | Строка, идентификатор неизменной версии условий; первоначально `product_v1` |
| name | Название продукта |
| currency | `RUB` |
| min_amount / max_amount | Десятичные строки; включительные границы суммы в рублях |
| min_term / max_term | JSON-целые; включительные границы срока в месяцах |
| annual_rate | Десятичная строка, доля за год: `0.20` означает 20%, `0.18` — 18% |

**Предложение команды:** условия хранятся в `credit_products` с составным PK
`(code, version)`. Изменять или удалять опубликованную версию нельзя, включая
прямой UPDATE/DELETE в БД; новые условия требуют новой строки версии.
Служебный `is_active` можно менять; частичный UNIQUE разрешает не более одной
действующей версии на код. Каталог показывает только действующие версии.
Миграция создаёт обе начальные версии; запуск seed аккаунтов для каталога не нужен.
API управления продуктами и историческим каталогом в T05 нет.

## Поля заявки

Сохраняются пути `POST /api/applications`, `GET/PATCH /api/applications/{id}`,
`POST /api/applications/{id}/submit`, `GET /api/applications/{id}/events`.
Создание возвращает 201, остальные успешные операции — 200.

Редактируемое тело POST/PATCH — JSON-объект; все поля необязательны в DRAFT:

| Поле | Тип ввода | Условия отправки |
| --- | --- | --- |
| company_name | string / null, ≤255 символов | Обязательно, не только пробелы |
| inn | string / null | Ровно 10 или 12 ASCII-цифр, без checksum |
| credit_purpose | string / null, ≤1000 символов | Обязательно, не только пробелы |
| amount | decimal string / JSON number / null | В пределах выбранного продукта |
| term | JSON integer / null, диапазон BIGINT | В пределах выбранного продукта |
| product_code | string / null, ≤64 символов | Существующий действующий продукт |
| monthly_revenue | decimal string / JSON number / null | Обязательно, >0 |
| monthly_operating_expenses | decimal string / JSON number / null | Обязательно, ≥0 |
| existing_monthly_debt_payments | decimal string / JSON number / null | Обязательно, ≥0 |

Максимум 64 символа для кода — **Предложение команды**, техническая граница
хранения. Неизвестный код разрешён в черновике, но отклоняется при submit.
Пустая/пробельная строка `product_code` сохраняется как `null`; другие коды
не обрезаются и не приводятся к верхнему регистру.

Деньги сохраняются как Decimal/NUMERIC без float и без округления. Во всех
денежных полях разрешены только конечные значения с максимум двумя знаками
после десятичной точки, включая черновики; `1.001`, `1.230`, NaN и Infinity
отклоняются. Рекомендуемый ввод — десятичная строка с точкой. JSON-числа также
разбираются сервером точно, но клиент обязан избежать потери точности до отправки.
В ответах и истории деньги всегда строки либо `null`. Число завершающих нулей
в ответах не фиксируется; сравнивать следует численное значение.

При POST пропущенные поля становятся `null`. При PATCH пропущенное поле не
меняется, явный `null` очищает его. Пустые/пробельные строки в денежных полях
и `term` превращаются в `null`; непустые строки для `term` недопустимы.
Булевы значения, дробный срок и срок за пределами BIGINT отклоняются.
Пустые текстовые поля, неполный ИНН, отрицательные деньги и сумма/срок вне
продуктовых границ допустимы в DRAFT, но не при отправке.
Расходы могут превышать выручку: отрицательный остаток не блокирует submit.
Финансового скоринга и проверки платёжеспособности в T05 нет.

Неизвестные и серверные поля в POST/PATCH дают 422. В частности, нельзя назначить
`product_version`, `id`, `status`, `owner_id`, `company_id`, `created_by`,
`version`, timestamps, actor, баллы или результаты проверок.

## Фиксация продукта и отправка

**Предложение команды:** клиент выбирает `product_code`. `product_version`
является серверным полем, в DRAFT всегда `null`. Submit без тела выбирает
действующую на момент команды версию указанного кода и проверяет её границы.
Версия в карточке каталога предназначена для отображения; клиент не передаёт её
в заявке. Если действующие условия изменились после чтения каталога, submit
использует новые условия или вернёт 422. Frontend должен перечитать каталог
и показать результат проверки. Проверки ожидаемой версии каталога в T05 нет.

Сервер блокирует заявку и выбранную строку продукта, проверяет старые пять
полей, обязательность новых полей, R>0, E≥0, D≥0 и включительные границы
суммы/срока. Затем в одной транзакции фиксирует `product_version`, SUBMITTED,
новый `updated_at`, увеличение `version` и событие SUBMITTED.
Пара `(product_code, product_version)` ссылается на неизменную строку каталога;
последующая смена действующей версии не меняет отправленную заявку.
Полный снимок условий восстанавливается по сохранённой паре в БД.

При ошибке не меняются ни данные, ни timestamps/version, ни история.
После SUBMITTED PATCH запрещён; повтор submit даёт 409.
Серверные сессии, HttpOnly-cookie, CSRF/Origin, права по owner_id и row lock
сохраняются. CLIENT изменяет только свои заявки; BANK_EMPLOYEE только читает.

## Примеры запроса и ответа

Создание неполного черновика:

```http
POST /api/applications
Content-Type: application/json
X-CSRF-Token: <токен текущей сессии>
Cookie: credit_pilot_session=<сессия>

{"product_code":"WORKING_CAPITAL","monthly_revenue":"200000.00"}
```

Дополнение своего черновика:

```json
{
  "company_name": "Синтетическая компания",
  "inn": "1234567890",
  "credit_purpose": "Пополнение оборотных средств",
  "amount": "100000.00",
  "term": 12,
  "product_code": "WORKING_CAPITAL",
  "monthly_revenue": "200000.00",
  "monthly_operating_expenses": "100000.00",
  "existing_monthly_debt_payments": "10000.00"
}
```

После `POST /api/applications/1/submit` — ответ (идентификаторы и время примерные):

```json
{
  "id": 1,
  "company_name": "Синтетическая компания",
  "inn": "1234567890",
  "credit_purpose": "Пополнение оборотных средств",
  "amount": "100000.00",
  "term": 12,
  "product_code": "WORKING_CAPITAL",
  "product_version": "product_v1",
  "monthly_revenue": "200000.00",
  "monthly_operating_expenses": "100000.00",
  "existing_monthly_debt_payments": "10000.00",
  "status": "SUBMITTED",
  "created_at": "2026-10-21T09:00:00Z",
  "updated_at": "2026-10-21T09:02:00Z",
  "company_id": 1,
  "created_by": 1,
  "owner_id": 1,
  "version": 3
}
```

POST/GET/PATCH возвращают ту же полную структуру; в DRAFT `product_version=null`.
`version` — версия заявки, `product_version` — версия условий продукта.

## История

Контракт оболочки события и пагинация `after_id`/`limit` не меняются.
DRAFT_CREATED содержит old=null/new для всех редактируемых полей, включая
продукт и финансы. DRAFT_UPDATED содержит только действительно изменённые поля.
SUBMITTED дополнительно фиксирует выбор версии:

```json
{"product_version":{"old":null,"new":"product_v1"}}
```

Деньги в changes — строки или null; product_code/version — строки или null.
Пустой/повторный PATCH не создаёт события. При ошибке журнала вся мутация
откатывается. Старые события не дополняются задним числом.

## Совместимость и ошибки

Пути, прежние поля, статусы DRAFT/SUBMITTED, авторизация и коды успеха сохранены.
Ответ заявки расширен пятью nullable-полями: product_code, product_version
и три финансовых значения. POST/PATCH со старыми пятью полями продолжают работать.
Миграции 0001–0003 не меняются; новая `0004_credit_products` добавляет каталог,
nullable-поля и ограничения точности/FK, без backfill данных заявок.
Старые DRAFT/SUBMITTED получают `null` в новых полях, сохраняют права,
статусы, даты, version и историю. Фиктивный продукт или финансы не назначаются.
Старые SUBMITTED читаются как прежде, не отправляются заново и не исправляются
обычным PATCH. Будущая банковская обработка неполных legacy-заявок потребует
отдельной процедуры; T05 её не реализует.

**Намеренное изменение поведения:** submit прежнего заполненного пяти-полевого
черновика теперь возвращает 422 до выбора продукта и заполнения трёх финансовых
полей. Также положительные сумма/срок вне границ продукта теперь дают 422.
Новые обязательные проверки не обходятся для старых черновиков.
Обработка денежных полей теперь также явно отклоняет невалидные JSON-константы
`NaN`/`Infinity`/`-Infinity` с 422 на уровне разбора JSON. Сообщение об избыточной
точности `amount` обобщено до `Money must have at most two decimal places`;
привязка ошибки остаётся `loc=["body","amount"]`.

| HTTP | Ситуация |
| --- | --- |
| 200 | Каталог, чтение, PATCH, submit |
| 201 | Создан DRAFT |
| 401 | Нет действующей серверной сессии |
| 403 | Недопустимая роль для команды, неверный CSRF/Origin |
| 404 | Заявка отсутствует или недоступна клиенту |
| 409 | PATCH/submit для заявки вне DRAFT, в том числе повтор submit |
| 422 | Ошибка JSON/типа/длины/точности, лишние поля, неполный submit, неизвестный/неактивный продукт, выход за границы, недопустимые финансы |
| 500 | Неожиданная серверная ошибка, в том числе БД/журнала; мутация откатывается |

Ошибки доступа/состояния: `{"detail":"..."}`. Ошибки полей:

```json
{
  "detail": [
    {"loc":["body","amount"],"msg":"Amount must be between 50000 and 3000000 RUB","type":"value_error"}
  ]
}
```

Ориентир для привязки ошибки в UI — `loc`; текст `msg` не является стабильным
кодом бизнес-ошибки. При базовых ошибках обязательности/типов проверки продукта
выполняются после исправления полей. Health по-прежнему делает SELECT 1:
200 при доступной БД, 503 при ошибке БД. Auth/me и восстановление CSRF не меняются.

## Граница интеграции

T05 предоставляет каталог, создание/чтение/редактирование/отправку и историю
для формы T07. UI, список своих заявок (часть T07), банковские команды,
проверки и скоринг здесь не реализуются. Нельзя считать весь T07 завершённым
на основании готового backend-контракта T05.
