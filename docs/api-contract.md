# API Credit Pilot

Актуален для `feature/slava-dore`. Машиночитаемый контракт:
[openapi.json](openapi.json); интерактивный — `/docs`; исполняемые сценарии —
[Postman collection](../api/README.md). Примеры содержат только синтетические данные.

## Общие правила

- Base URL `http://localhost:5173` через nginx или `http://localhost:8000` напрямую.
- Cookie-сессия `HttpOnly`, `SameSite=Lax`, `Secure` настраивается для HTTPS.
  После login клиент сохраняет cookie и `csrf_token`. Все изменения, включая
  logout, требуют `X-CSRF-Token`. Origin проверяется, если прислан.
- `/api/me` возвращает пользователя, не выдаёт CSRF. Для новой вкладки без токена
  перед изменением нужен повторный вход. Пароль/session-token не возвращаются в JSON.
- CLIENT видит только заявки с собственным `owner_id`. BANK_EMPLOYEE видит
  отправленные заявки. Чужой объект скрывается 404; неправильная роль — 403.
- Деньги в ответах — **строки**, максимум два десятичных знака на входе. JSON
  числа тоже декодируются через Decimal; лишняя точность отклоняется, не округляется.
- Даты ISO 8601, UTC; интерфейс показывает МСК. Все статусы, ID, версии и время
  назначает сервер. Неизвестные поля тела команды запрещены.
- 401 — нет сессии; 403 — роль/CSRF/Origin; 404 — объект недоступен;
  409 — состояние/версия/повтор с другим содержимым; 422 — вход или бизнес-правило.
- На ошибке валидации заявка, версия, история и timestamps не меняются.
  Успешные мутация и событие сохраняются в одной транзакции.

## Анкета и каталог

Поля: `company_name`, `inn`, `credit_purpose`, `amount`, `term`, `product_code`,
`monthly_revenue`, `monthly_operating_expenses`, `existing_monthly_debt_payments`.
В черновике все могут отсутствовать/null; на submit все обязательны. ИНН — 10/12
цифр, сумма/выручка >0, расходы и выплаты ≥0, срок — целые месяцы. Ограничения
продукта дополнительно проверяются на сервере. Компания может отличаться от
профиля: право определяется владельцем заявки, не `company_id`.

Поля ответа заявки дополнительно: `id`, `status`, `owner_id`, `company_id`,
`product_version`, `version`, `created_at`, `updated_at`. Точный состав — OpenAPI.
Продукт содержит `code`, `version`, `name`, `currency`, `min_amount`, `max_amount`,
`min_term`, `max_term`, `annual_rate` (доля, например `0.20`, не проценты).

Расчёт платежа:

```json
{"product_code":"WORKING_CAPITAL","amount":"600000.00","term":18}
```

Ответ: `monthly_payment` и `annual_rate`, строки. Расчёт не создаёт предложение.

PATCH/submit принимают необязательный заголовок `If-Match: 3` с текущей версией.
Интерфейс всегда передаёт его. Заголовок оставлен необязательным для совместимости
с T01/T05. Нет ключа идемпотентности у создания черновика: при потере ответа
нужно проверить список, не слепо повторять POST.

GET списка: `status`, `q` (часть названия, точный ИНН/номер), `limit=20` (1–100),
`offset=0` (0–1000000). Ответ `{items,total,limit,offset}`; сортировка по
`updated_at DESC,id DESC`. История: `limit=100`, максимум 100, `after_id=0`;
сортировка по ID ASC (следующая страница: after_id равен последнему ID), ответ — массив. Загрузка следующих страниц обязательна
для полного журнала длинной заявки.

## Бизнес-команды и повторы

Каждая новая команда возвращает обновлённую заявку и требует:

```json
{"expected_version":3,"command_id":"7ab50210-d561-43e5-83ce-588ae53c54a6"}
```

`command_id` — новый UUID для нового намерения. Точный повтор тем же актором,
с тем же телом и маршрутом возвращает сохранённый ответ без второй мутации.
Другое тело/актор/действие с тем же ключом → 409. При потере ответа повторяют
**старый UUID и старую expected_version**, а не создают новое намерение.
Получив подтверждение, нужно перечитать досье: сохранённый ответ повтора может
содержать более раннюю версию, если после него уже прошли другие команды.

Состояния и разрешённые переходы: [application-flow.md](application-flow.md).
`allowed_actions` в досье помогает интерфейсу, но все ограничения повторно
проверяются сервером под row lock.

Проверки сохраняют RUNNING и CHECKS_STARTED отдельной транзакцией, затем
результат и CHECKS_COMPLETED/FAILED — второй. Сбой источника оставляет CHECKING,
но не положительный результат. Ошибки: SOURCE_UNAVAILABLE, SOURCE_INVALID,
PROCESSING_ERROR, INTERRUPTED. Повтор новой командой разрешён после FAILED;
RUNNING разрешено заменить только через 30 секунд. Это учебный порог команды.

## Запрос и ответ

К полям команды банк добавляет:

```json
{
  "message":"Уточните регулярные расходы без разовой покупки",
  "fields":["monthly_operating_expenses"],
  "document_kind":"FINANCIAL_REPORT"
}
```

Разрешены company_name, credit_purpose и три финансовых поля. `fields` может
быть пустым; тогда можно запросить документ или текстовое объяснение.
`document_kind` — FINANCIAL_REPORT / PURPOSE_EVIDENCE / null.

Ответ клиента:

```json
{
  "explanation":"Исключили разовую покупку станка из регулярных расходов",
  "fields":{"monthly_operating_expenses":"400000.00"},
  "documents":[{"name":"report.txt","content":"СИНТЕТИЧЕСКИЙ ОТЧЁТ\nРасходы: 400000.00 RUB"}]
}
```

`fields` должен содержать ровно запрошенные поля. Для запрошенного документа
обязателен минимум один файл. Максимум три TXT/CSV, каждый до 64 КиБ UTF-8,
без бинарных управляющих символов/путей в имени. Текст хранится в БД, в истории
только ID документов. Скачать можно после серверной проверки владельца/роли.
Новые значения и закрытие запроса атомарны; статус SUBMITTED, нужна новая оценка.

## Решение, договор и выдача

Предложение: `kind=OFFER`, `reason_code=STANDARD`, `explanation` ≥10 символов.
Для меньшей суммы: `reason_code=COUNTER_OFFER`, `offered_amount` строкой.
Сервер повторно рассчитывает условия по сохранённым исходным данным и политике;
запрошенная сумма не перезаписывается. Срок и продукт не меняются.

Отказ: `kind=REJECT`, `reason_code` AFFORDABILITY / CREDIT_HISTORY /
INACTIVE_BUSINESS / HIGH_RISK, `explanation`. Причина обязана подтверждаться
фактами текущего снимка. Отсутствие данных не равно высокому риску.

Подпись: `decision_id` и `confirmed=true` дополнительно к Command. Сохраняются
текст демонстрационного договора, SHA-256, actor и время. Выдача принимает только
Command и берёт сумму из согласованного решения; уникальные ограничения БД
не позволяют повторить договор/выдачу для заявки.

## Досье и аналитика

Досье читает согласованный снимок REPEATABLE READ: application, runs (новые
сначала), information_requests, decision, contract, disbursement, documents,
contract_preview и allowed_actions. Run содержит input_snapshot, product_snapshot,
checks, assessment, state, error_code и время. Assessment включает score_version,
policy_version, factors, risk/score, DSCR, платёж, blockers, alternative и ML.
Клиент видит те же объяснения риска и решений. Это сознательная прозрачность демо.

Аналитика считает уникальные заявки, когда-либо достигавшие этапа, по событиям.
Повторная проверка не увеличивает воронку. Текущая очередь считается по статусам.
Причины ожидания: CHECKS_NOT_STARTED, CHECKS_RUNNING, CHECKS_FAILED,
DATA_INCOMPLETE, BANK_DECISION, CLIENT_REPLY, CLIENT_SIGNATURE, BANK_DISBURSEMENT.
Возраст — время с последнего изменения заявки; >24 ч — ориентир внимания, не
банковский SLA. Отказ закрывает заявку и исключает её из активных задержек.
