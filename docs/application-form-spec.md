## 1. Цель и границы функциональности

Анкета позволяет авторизованному предпринимателю с ролью CLIENT выбрать
демонстрационный кредитный продукт, постепенно заполнить сведения, сохранить
неполный черновик, вернуться к нему и передать заявку сотруднику банка.
Результат отправки — `SUBMITTED`, а не одобрение, договор или выдача.
Пользователь работает только с синтетическими сведениями своей тестовой компании.
Два клиента одной компании не получают доступа к заявкам друг друга (D, S).

| Область | Факт T01 | Целевой MVP / зависимость |
| --- | --- | --- |
| Доступ | Серверные login/logout/me, cookie и CSRF, CLIENT/BANK_EMPLOYEE | T06: интерфейс входа, bootstrap и восстановление после reload |
| Продукты и финансы | Отсутствуют в БД/API | T05: два продукта, версии, три финансовых поля, явное расширение submit |
| Заявка | Создание/чтение/PATCH/submit пяти полей; DRAFT/SUBMITTED | T07: форма, каталог, список своих заявок, просмотр и история |
| История | DRAFT_CREATED/DRAFT_UPDATED/SUBMITTED, атомарная запись | Отображение в T07; новые банковские события позже |
| Интерфейс | Только health-страница, см. [main.tsx](../frontend/src/main.tsx) | Все экраны раздела 7 ещё предстоит реализовать |

Основание: R03/R05/R13/R17/R19 в R; план P. Для A01 создаётся только этот файл.
Backend/frontend, миграции, зависимости и другие документы не меняются.
ORM-рефакторинг T02 не требуется. Не добавляются паспортные сведения, контакты,
адреса, ОКВЭД, файлы отчётности, поручители или новые обязательные банковские поля.
Регистрация аккаунтов, реальные БКИ/ФНС, реальные подпись/деньги и LLM вне границ.
Скоринг, банковские решения и уточнения описываются существующими A/D/F и здесь
не проектируются заново. Основной путь полностью внутри веб-продукта.

## 2. Пользовательский сценарий

Следующая таблица описывает целевой UI. API действий существует только там,
где это отмечено в разделе 6. Конкретные надписи, блокировки кнопок и порядок
показа ошибок — **Предложение аналитика**, согласование Q06 в разделе 9.

| Шаг / действие | Предусловие | Результат | Ошибки и поведение UI |
| --- | --- | --- | --- |
| 1. Войти | Есть локальный демоаккаунт, сервер доступен | Login устанавливает cookie, возвращает пользователя и CSRF; UI проверяет CLIENT | 401: «Неверный логин или пароль»; 422: исправить поля; 403 Origin: общая ошибка доступа; при ожидании кнопка заблокирована, пароль не журналируется |
| 2. Просмотреть и выбрать продукт | Сессия CLIENT подтверждена через /api/me; каталог T05 загружен | Видны назначение, пределы, ставка и отметка синтетических условий | Загрузка/ошибка/повтор чтения; пустой каталог — объяснение отсутствия продуктов, создание недоступно; выбор сам по себе не означает создание заявки |
| 3. Создать DRAFT | CLIENT, действующий CSRF; пользователь нажал «Начать заявку» | POST возвращает 201, серверный id и DRAFT; UI открывает созданную заявку | 401/403: вход/доступ; 422: сообщение; при потере ответа не повторять POST автоматически, см. 6.4 |
| 4. Заполнить анкету | Получен свой DRAFT | Локальные поля формы, явно показано «Есть несохранённые изменения» | Неверный ввод остаётся в форме; нет обещания сохранения до ответа API; серверные поля недоступны для ввода |
| 5. Сохранить неполный черновик | Свой DRAFT и CSRF, значения проходят структурную проверку | PATCH сохраняет переданные поля; ответ 200 — основание показать «Черновик сохранён» | Не требовать заполнения всех полей; 422 — ошибки у полей; 409 — перечитать состояние; при сети форма сохраняет локальный ввод, успешное сохранение не показывать |
| 6. Вернуться к заявке | Сессия действительна либо выполнен новый вход; известен id / доступен будущий список | GET загружает сохранённые серверные значения и статус | 401 — вход; 404 — «Заявка не найдена или недоступна»; не выдавать чужие данные и не создавать новую заявку вместо пропавшей |
| 7. Проверить перед отправкой | Свой DRAFT | UI проверяет обязательность, формат и после T05 пределы/финансы; при изменениях сначала выполняет PATCH | Невалидные поля выделены; фокус на первой ошибке; при ошибке PATCH submit не вызывается; промежуточный отдельный экран подтверждения не требуется |
| 8. Отправить | Сохранённые данные валидны; CSRF есть; PATCH завершён | POST /submit без тела проверяет именно сохранённую заявку | 422 — объяснить поля; 409 — перечитать; сеть с неизвестным исходом — сначала GET, не показывать ложный успех |
| 9. Получить SUBMITTED | Submit вернул 200 и серверный статус SUBMITTED, либо статус подтверждён GET после обрыва | Экран результата, номер, сохранённые условия, история; редактирование закрыто | Не устанавливать статус локально по нажатию; сообщение «Заявка отправлена», без обещания одобрения |
| 10. Посмотреть следующие действия | Своя доступная заявка | SUBMITTED: «Ожидайте начала проверки»; история читается отдельно; UI перечитывает ресурс | Сбой истории не скрывает подтверждённую заявку; отдельное сообщение и повтор чтения; будущие действия показывать только после соответствующих backend-задач |

Целевая навигация: вход → каталог → DRAFT → сохранение/возврат → SUBMITTED.
Источники: F «Фактически реализованный путь T01» и «Целевой сквозной путь»,
A «Кабинеты», D «Поля заявки и валидация». Восстанавливаются только успешно
сохранённые данные. Сохранение незаписанного ввода после закрытия/reload не обещается.

После SUBMITTED ожидается обработка сотрудником; клиент не запускает проверки.
Целевые CHECKING/UNDER_REVIEW/NEEDS_INFO/OFFERED/REJECTED/SIGNED/DISBURSED —
последующие задачи, не текущие значения Enum Status. Ответ на запрос уточнений
будет отдельной командой с разрешёнными финансовыми полями и пояснением:
обычный PATCH запрещён после отправки, в том числе в NEEDS_INFO (D, F).

## 5. Правила валидации

### 5.1. Сохранение неполного DRAFT

**Факт T01:** POST принимает `{}`; PATCH принимает подмножество пяти полей.
Пропущенное поле PATCH не меняется, явный null очищает его. Неверный тип,
company_name >255, credit_purpose >1000, нецелый/выходящий за BIGINT term,
нечисловая/неконечная/избыточно точная amount отклоняются с 422.
Структурно корректный, но неполный DRAFT сохраняется; полнота и положительность
проверяются submit. Неизвестные и серверные поля отклоняются.

**Целевой MVP T05:** новые поля nullable в черновике, Decimal сохраняется точно,
история охватывает новые бизнес-поля, новая миграция сохраняет старые записи (D, P).
**Предложение аналитика Q03:** проверять точность/конечность финансовых значений
уже при сохранении, обязательность и знак — при submit; пустой числовой ввод
передавать null. Неизвестный ненулевой код/версию продукта отклонять при
сохранении. Точный контракт сохранения новых полей требует решения T05,
включая допустимость отрицательных финансовых чисел в DRAFT. Это не действующие
правила текущего API и не повод менять согласованные пороги при submit.

### 5.2. Отправка и продуктовые границы

**Факт T01:** submit читает сохранённые значения, проверяет все пять полей 4.1
и состояние DRAFT. Успех: 200, SUBMITTED, рост version, новый updated_at,
ровно одно событие SUBMITTED в той же транзакции. Состояние меняет только команда
submit; PATCH статуса запрещён. Никаких обязательных финансов/продукта пока нет.

**Целевой MVP T05:** дополнительно требуются существующий продукт с фиксируемой
версией, R >0, E ≥0, D ≥0 и включительные пределы раздела 3. Ноль расходов/долга
валиден, null не означает ноль. Для WORKING_CAPITAL сумма от `"50000"` до
`"3000000"`, срок 3–24; для EQUIPMENT от `"100000"` до `"5000000"`, срок 6–36.
Предлагаемый UI-текст: «Сумма для выбранного продукта — от … до … ₽» /
«Срок для выбранного продукта — от … до … месяцев». Подставляются условия
выбранной серверной версии, не произвольные числа frontend.

Расходы > выручки не блокируют отправку: отрицательный денежный остаток допустим
и влияет на будущую оценку. Высокие действующие платежи сами по себе не новая
ошибка анкеты. Не добавлять пороги DSCR, возраст бизнеса, проверку checksum
ИНН, кредитное решение или успешность fixture к submit. Политика предложения
проверяется отдельно в банковском процессе (A, D, F).

Старые DRAFT после T05 дополняются постепенно. Старые SUBMITTED без новых
сведений не переписываются, не дополняются фиктивными значениями и не допускаются
к будущему рассмотрению без отдельной контролируемой процедуры (P; Q07).

### 5.3. Клиентская и серверная проверка

Клиентская проверка — удобство интерфейса T07, **Предложение аналитика Q06**:
показывать ограничения до ввода, при сохранении проверять структурные ограничения,
при отправке — также полноту и условия продукта. Ошибки обязательности не должны
препятствовать отдельной кнопке сохранения неполного DRAFT. После неуспешной
отправки поля остаются заполненными; ошибки рядом с полем и общая сводка.

Серверная проверка обязательна независимо от UI: сессия, CSRF/Origin, роль,
owner_id, статус и входы; в T05 добавятся продукт/финансы. Скрытая кнопка
не контроль доступа. Пустой либо не меняющий данные PATCH в DRAFT оставляет
version, timestamps и историю прежними. В SUBMITTED даже пустой PATCH — 409.
При 422 конкретная неуспешная команда не меняет ни данные, ни состояние,
ни timestamps, ни version, ни события (C, D, E).

PATCH перед submit — две разные транзакции. Если PATCH успешен, а submit
отклонён, сохраняется результат PATCH и DRAFT; отката уже сохранённых правок
нет. Ошибка записи события откатывает соответствующую бизнес-мутацию целиком.

### 5.4. Числовой ввод и точность

Деньги передаются десятичными строками, хранятся Decimal/NUMERIC, возвращаются
строками; не использовать JS Number/parseFloat для денежных расчётов/сравнений.
Фактически текущий API также принимает JSON-число amount и читает его через
DecimalJSONRequest без промежуточного float (C). Для UI выбран строковый формат.
`"1.230"` отклоняется так же, как `"1.001"`: лишний третий знак не отбрасывается.
`NaN`, ±Infinity, произвольный текст — ошибка; пустота — null, не ноль.
`term` передавать JSON-целым; строки, дроби и boolean отклоняются.

**Предложение аналитика Q04:** для MVP интерфейс явно просит точку как разделитель,
без автоматического исправления запятых, разделителей тысяч и экспоненты.
Денежный ввод/сравнение остаются строковыми либо используют точную десятичную
арифметику. Это ограничение UI, не утверждение, что backend запрещает все формы
числовой записи, поддерживаемые Decimal. Не обрезать пробелы текстовых полей
или цифры ИНН незаметно; ошибки исправляет пользователь. Расчёт платежа и
округление отображения из A не означают округления входных сумм; калькулятор
платежей не добавляется в A01.

### 6.3. Сессия, CSRF и ошибки

Факт S/A: серверная сессия на 8 часов; cookie `credit_pilot_session` HttpOnly,
SameSite=Lax, Path=/api, Secure по конфигурации. Для UI используется same-origin
proxy и cookie; session-token не читается из JS. На мутациях кроме login нужны
`X-CSRF-Token`, допустимый Origin при его наличии и допустимый Sec-Fetch-Site.
Сервер получает пользователя/роль/владельца из сессии; company_id не даёт прав.

Предложение команды для T06 из A: после login хранить **только csrf_token**
в sessionStorage; bootstrap — GET /api/me и проверка пользователя/роли по серверу.
Reload той же вкладки сохраняет токен; /api/me его не восстанавливает, csrf_hash
необратим. При пустом storage и живой cookie доступны чтения, но изменения
требуют явного повторного входа. При 401/logout очищать клиентский CSRF;
при новом login заменять. Другие вкладки могут получить несоответствие cookie
и токена: требуется повторный вход, не автоматический retry команды.
Это пока не реализовано; отдельного endpoint восстановления CSRF нет.

| HTTP | Значение текущего API | Реакция будущего UI — Предложение аналитика Q06 |
| --- | --- | --- |
| 401 | Нет/истекла/отозвана сессия; на login также неверные реквизиты | Показать вход; очистить устаревший CSRF; вернуться к заявке после успешного входа с повторным GET, не повторять изменения автоматически |
| 403 | Неподходящая роль, неверный CSRF, запрещённый Origin/cross-site | Различать причины по известному detail; при CSRF просить повторный вход, при роли — «Действие недоступно», при Origin — ошибка доступа, не вход по кругу |
| 404 | Заявки нет или CLIENT не её владелец, даже в той же компании | Одинаковое сообщение о недоступности; не раскрывать существование чужой заявки |
| 409 | Сейчас заявка не DRAFT, включая повтор submit | Перечитать заявку; если SUBMITTED — просмотр результата; не обещать конфликт expected_version, его пока нет |
| 422 | Неверный тип, формат, неизвестное поле, неполнота submit; T05 добавит продукт/финансы | Обработать detail как массив ошибок, сопоставить loc с полями, показать сводку для неизвестной ошибки; не менять статус локально |

Текущий submit формирует ошибки `{loc:["body", field], msg, type}`. Ошибки
валидации тела FastAPI могут содержать дополнительные поля: UI не должен
предполагать один неизменный английский текст или выводить полное тело ошибки
с паролями/токенами. Вне 4xx: сеть/5xx — понятная общая ошибка, исход мутации
может быть неизвестен. Нет обещания, что сервер ничего не сохранил при обрыве.

### 6.4. Конкурентность и повтор команд

PATCH/submit защищены row lock; version растёт при реальном изменении.
Проверки ожидаемой версии сейчас нет, разные записи одного поля работают
как last-write-wins. UI не должен выдавать фиктивную защиту от устаревшей формы.
**Предложение аналитика Q06:** на время мутации блокировать повторные клики и
параллельные команды формы. Перед submit дождаться ответа PATCH; результат
брать с сервера. Обновление экрана по A — периодический GET раз в несколько
секунд и перечитывание после команды; точный интервал отдельный UI-параметр.

POST создания не идемпотентен. При потере ответа id может быть неизвестен:
не повторять автоматически; после реализации списка сначала проверить его,
до этого показать неопределённый исход и не обещать восстановление номера (Q05).
При обрыве PATCH/submit с известным id сначала GET; только после сверки серверного
состояния пользователь решает о повторе. Повтор submit вернёт 409 без нового
события; PATCH с уже записанными значениями не меняет историю. Потеря ответа
не является разрешением создавать новую заявку или отправлять её заново.

Все три wireframe — **Предложение аналитика Q06** для T07, не существующий UI.
Используются три смысловых экрана без назначения новых frontend URL.
Вход T06 предшествует им; сотрудник с ролью BANK_EMPLOYEE работает в отдельном
кабинете и не заполняет клиентскую форму.

### 7.1. Выбор кредитного продукта

```text

Выберите кредитный продукт
Синтетические учебные условия команды, не предложение Альфа-Банка

Оборотный кредит                    Кредит на оборудование
Для оборотных средств               Для покупки оборудования
```

загрузить продукты» и повтор чтения. Пусто: сообщение без фиктивных карточек.
Создание: индикатор «Создаём черновик», кнопки создания блокируются; 201 → форма
с полученным id. При неизвестном исходе POST — сообщение из 6.4. «Мои заявки»
зависит от списка T07; не вести на вымышленный рабочий экран до его реализации.

Продукт/финансы появляются после T05. При GET форма в состоянии загрузки,

затем «Черновик сохранён» только после 200; no-op ответ тоже успешен, без нового
события. Отправка сначала валидирует и сохраняет изменения, затем submit;
при ожидании все команды формы заблокированы. При ошибке сохраняются введённые
значения; сводка помогает перейти к первому полю. Переход к списку и смена
продукта с несохранёнными изменениями требуют выбора «Сохранить / Остаться /
Выйти без сохранения» — новое UX-предложение Q06, без автосохранения.

При reload восстанавливаются серверные поля, а не потерянный локальный ввод.
При пустом CSRF: «Для сохранения и отправки войдите повторно»; просмотр доступен
при живой сессии. Редирект не должен означать успешное сохранение. Если GET
возвращает SUBMITTED, сразу экран просмотра, даже если исходная ссылка была
открыта как форма. Смена продукта недоступна после отправки.

Успех основан на ответе submit/GET. Кнопок редактирования/повторной отправки нет.
Автообновление перечитывает ресурс, не запускает банковскую обработку. Ошибка
фонового обновления не подменяет последний подтверждённый статус: показать
«Не удалось обновить данные» и возможность повтора. История загружается отдельно,
имеет состояния ожидания/ошибки/пагинации; пустая история не выдумывается.

зоны пользователя — UX-предложение Q06, исходное время не изменяется.
Будущие банковские статусы отображаются по F после реализации соответствующих
команд, а не автоматически дорисовываются после SUBMITTED.

## 8. Приемочные критерии Given / When / Then

«Сейчас API» означает, что сценарий применим к текущему коду, **не отчёт о запуске**
тестов в A01. Все браузерные проверки требуют T06/T07; новые поля/продукты — T05.
Новые предложения Q01–Q06 проверяются после согласования и реализации.
Каждый негативный сценарий выполняется с остальными валидными предусловиями,
чтобы не смешивать ошибку сессии, CSRF, роли, формата и статуса.

| ID | Given | When | Then | Доступность / источник |
| --- | --- | --- | --- | --- |
| AC01 | CLIENT вошёл и имеет CSRF | Создаёт `{}`, затем сохраняет только company_name | 201/200, DRAFT с неполными полями; повторный GET возвращает сохранённое | Сейчас API; UI T06/T07. C/D |
| AC02 | Свой DRAFT с пятью корректными сохранёнными полями | Выполняет submit | 200, SUBMITTED, version +1, updated_at обновлён, ровно одно SUBMITTED | Сейчас API; UI T06/T07. C/E/F |
| AC03 | После T05 выбран существующий продукт, сумма/срок в границах, R >0, E/D ≥0 | Сохраняет и отправляет полную заявку | SUBMITTED с серверно зафиксированной версией продукта и финансовыми полями | После T05; UI T06/T07. A/D/P; Q01/Q02 |
| AC04 | В DRAFT null/пустые обязательные поля | Отправляет | 422 с указанием полей, без изменения данных/version/timestamps/истории этой командой | Пять полей сейчас API; новые — T05; UI T06/T07. C/D |

основную БД/volume не очищать. В A01 достаточно проверки документа.

(A/D/F), не скрытой дополнительной проверкой формы.

## 10. Definition of Done задачи A01

Это критерии готовности аналитического артефакта, а не реализации T05/T06/T07.
Разработчики могут использовать подтверждённые правила сразу; Q01–Q06 должны
быть закрыты ответственными до реализации затронутых неопределённых деталей.
Публикация спецификации не означает их согласования.

- [ ] Прочитаны AGENTS, README и пять проектных документов, сверены C/S/E,
  текущая схема и границы frontend; зафиксирован базовый commit анализа.
- [ ] В документе присутствуют десять разделов A01, текущая и будущая функции
  отделены от новых предложений, требования организаторов не подменены правилами команды.
- [ ] Таблицы охватывают пять текущих полей, ссылку product_code/version и три
  будущих финансовых поля: типы, обязательность, ограничения, примеры, ошибки и источники.
